# Doc-Sync Best Practices

## When to Use Doc-Sync

### ✅ Good Use Cases

1. **After Feature Implementation**
   ```bash
   # Feature complete → commit code → run doc-sync
   git commit -m "feat: add article search endpoint"
   @skill:doc-sync
   ```

2. **API Changes**
   - New endpoints added
   - Endpoint signatures changed (query params, response models)
   - Authentication requirements modified

3. **Database Schema Changes**
   - New tables added
   - Columns added/modified
   - Indexes/constraints changed
   - Migrations applied

4. **Frontend Module Changes**
   - New TypeScript modules created
   - Exported functions/classes modified
   - Component interfaces changed

### ❌ Bad Use Cases

1. **Trivial Changes**
   ```bash
   # Just a typo fix - skip doc-sync
   git commit -m "fix: typo in comment"
   # No need for @skill:doc-sync
   ```

2. **Work in Progress**
   ```bash
   # Code not ready - don't run doc-sync yet
   git commit -m "wip: experimenting with search"
   # Wait until feature is complete
   ```

3. **Only Documentation Changes**
   ```bash
   # Already editing docs manually - no sync needed
   git commit -m "docs: update API guide"
   # Doc-sync is for code → docs direction
   ```

## Documentation Quality Guidelines

### 1. Review Auto-Generated Content

**Doc-sync generates TODOs - you MUST review them:**

```yaml
# ❌ BAD - Leaving TODOs unreview
- path: "/api/v1/articles/search"
  description: "TODO: Add description - auto-detected"  # LEFT AS-IS!
  service:
    # TODO: Add $ref to functionality module  # LEFT AS-IS!
```

```yaml
# ✅ GOOD - Completing TODOs
- path: "/api/v1/articles/search"
  description: "Full-text search for articles with query filtering by type and parent category"
  service:
    $ref: "../functionality/budget-management.yaml#/module/services/1"
```

### 2. Add Context, Not Just Signatures

**Doc-sync extracts signatures, YOU add context:**

```yaml
# ❌ BAD - Just signature
query_params:
  q: "string (required)"
  type: "string (optional)"

# ✅ GOOD - Signature + context
query_params:
  q: "string - search query (required). Searches in article name, code, and description. Minimum 3 characters."
  type: "income | expense (optional) - filter results by transaction type"
```

### 3. Document Error Responses

**Doc-sync only detects success responses - YOU add errors:**

```yaml
# Auto-generated by doc-sync:
response:
  status: 200
  body:
    articles: "array of article objects"

# YOU SHOULD ADD:
errors:
  - status: 400
    description: "Invalid query parameter (q too short)"
  - status: 401
    description: "Unauthorized - missing or invalid JWT token"
  - status: 422
    description: "Validation error - invalid type value"
```

## Workflow Integration Best Practices

### 1. Run Doc-Sync Before PR

**Recommended workflow:**
```bash
# 1. Complete feature
git commit -m "feat: add article search"

# 2. Sync documentation
@skill:doc-sync
# Review and approve updates

# 3. Commit docs
git add docs/
git commit -m "docs: sync endpoint documentation for article search"

# 4. Create PR
@skill:pr-automation
```

### 2. Use --check for Safety

**Before making changes, preview with --check:**
```bash
# Dry-run mode
@skill:doc-sync --check

# Review output:
# ⚠️ Staleness Issues:
#   1. Missing component: GET /api/v1/articles/search

# Then apply:
@skill:doc-sync
```

### 3. Batch Related Changes

**Don't run doc-sync after every commit:**
```bash
# ❌ BAD - Too frequent
git commit -m "feat: add search endpoint"
@skill:doc-sync
git commit -m "feat: add pagination to search"
@skill:doc-sync
git commit -m "feat: add sorting to search"
@skill:doc-sync

# ✅ GOOD - Batch related commits
git commit -m "feat: add search endpoint with pagination and sorting"
@skill:doc-sync
```

## Handling Conflicts

### 1. Manual Changes vs Auto-Generated

**What if you manually edited docs, then doc-sync detects changes?**

**Strategy: Merge manually**
```bash
# Doc-sync detects changes to already-documented endpoint
@skill:doc-sync --check

# Output:
# ⚠️ Signature mismatch: POST /api/v1/articles
#   Code has: query param 'validate_hierarchy'
#   Docs missing this param

# Action: Review code changes
# - If intentional: Approve doc-sync update
# - If experimental: Skip update, mark as WIP in docs
```

### 2. Complex Restructuring

**When refactoring breaks doc-sync mapping:**

**Example:**
```python
# Before: backend/app/api/v1/endpoints/articles.py
@router.get("/articles")

# After: Renamed file
# backend/app/api/v1/endpoints/budget_articles.py
@router.get("/articles")
```

**Doc-sync can't auto-detect file renames.**

**Action:**
1. Manually update architecture_refs in affected skills
2. Run doc-sync to detect signature changes
3. Update $ref links in YAML files

## Performance Tips

### 1. Use Incremental Mode (Default)

**Doc-sync only analyzes git diff by default:**
```bash
# Fast - only changed files
@skill:doc-sync

# Slow - full codebase validation
@skill:doc-sync --validate
```

### 2. Skip Validation for Simple Changes

**If you KNOW docs are up-to-date:**
```bash
# Skip doc-sync for trivial changes
git commit -m "refactor: rename internal variable"
# No @skill:doc-sync needed
```

## Common Pitfalls

### 1. Forgetting to Commit Docs

```bash
# ❌ BAD
git commit -m "feat: add search endpoint"
@skill:doc-sync
# Approves updates, but FORGETS to commit docs!
git push  # Docs updates NOT pushed!

# ✅ GOOD
git commit -m "feat: add search endpoint"
@skill:doc-sync
git add docs/
git commit -m "docs: sync with code changes"
git push  # Both code and docs pushed
```

### 2. Ignoring Staleness Warnings

```bash
@skill:doc-sync --check

# Output:
# ⚠️ 3 staleness issues found

# ❌ BAD - Ignoring warnings
# Proceeds to PR without fixing

# ✅ GOOD - Addressing warnings
@skill:doc-sync  # Fix issues
# Review and approve updates
```

### 3. Over-relying on Auto-Generation

**Doc-sync is a TOOL, not a replacement for thoughtful documentation:**

```yaml
# ❌ BAD - Just auto-generated, no thought
- path: "/api/v1/articles/search"
  description: "TODO: Add description"  # Left as TODO!
  query_params:
    q: "string"  # No context!

# ✅ GOOD - Auto-generated + human refinement
- path: "/api/v1/articles/search"
  description: "Full-text search for budget categories supporting hierarchical filtering"
  query_params:
    q: "string - search query (min 3 chars). Searches name, code, description fields."
  notes: |
    Search is case-insensitive and uses PostgreSQL full-text search.
    Results are ranked by relevance (ts_rank).
    Performance: ~50ms for typical query on 1000 categories.
```

## Changelog Best Practices

### 1. Significance Badges

**Use correct significance level:**
- 🔧 MINOR - Bug fixes, documentation updates, small improvements
- ⭐ MAJOR - New features, significant changes
- ⚠️ BREAKING - Breaking changes requiring migration

```markdown
# ❌ BAD - Wrong significance
### 2026-02-09: Fix typo in API docs ⚠️ BREAKING

# ✅ GOOD - Correct significance
### 2026-02-09: Fix typo in API docs 🔧 MINOR
```

### 2. Link to Related Issues/PRs

```markdown
# ✅ GOOD - Context + links
### 2026-02-09: Add article search endpoint ⭐ MAJOR

- **Change:** Implemented full-text search for articles
- **Issue:** Closes #123
- **PR:** #456
- **Migration:** No breaking changes
```

### 3. Keep Recent Changes Visible

**Limit changelog to ~10 recent entries:**
```markdown
## Recent Changes

### 2026-02-09: Add article search ⭐ MAJOR
### 2026-02-08: Fix authentication bug 🔧 MINOR
...
### 2026-01-30: Initial release 🎉

## Archive

[Older changes moved to docs/CHANGELOG_ARCHIVE.md]
```

## Summary

**Golden Rules:**
1. ✅ Run doc-sync after feature completion (not every commit)
2. ✅ Always review and complete TODOs in auto-generated docs
3. ✅ Add context beyond signatures (errors, examples, performance notes)
4. ✅ Use --check for preview before applying
5. ✅ Commit docs separately from code (clear git history)
6. ✅ Address staleness warnings promptly
7. ❌ Don't over-rely on auto-generation
8. ❌ Don't skip doc-sync for significant changes
9. ❌ Don't forget to commit docs after approval

**Doc-sync is your assistant, not your replacement. Think critically about documentation quality!**
