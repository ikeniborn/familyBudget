## Architecture Overview

### Database Schema Management (Alembic-Only)

Family Budget uses **Alembic** for all database schema management. The old 2-tier system (schema/*.sql) has been **deprecated** and replaced with proper versioned migrations.

```
Migration System Evolution:
┌─────────────────────────────────────────────────────────────┐
│ OLD (Deprecated): 2-Tier System                             │
├─────────────────────────────────────────────────────────────┤
│ Tier 1: backend/db/schema/*.sql (base DDL)                 │
│ Tier 2: backend/db/migrations/ (Alembic - NOT USED)        │
│ Tracking: schema_migrations table (custom checksums)       │
│ Use case: Development Mode (full DB recreation)            │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ NEW (Current): Alembic-Only System                          │
├─────────────────────────────────────────────────────────────┤
│ Location: backend/db/migrations/versions/*.py              │
│ Tracking: alembic_version table (built-in)                 │
│ Use case: ALL environments (dev/staging/prod)              │
│ Features: Versioning, Rollback, Autogenerate               │
└─────────────────────────────────────────────────────────────┘
```

### Database Schema

Family Budget implements advanced database patterns:

- **SCD Type 2** - Historical tracking for dimension tables
- **Closure Table** - Efficient hierarchical queries for article categories
- **Star Schema** - Optimized for analytics queries
- **Shared Family Budget Model** - All users see all transactions

## Alembic Workflow

### Development Workflow

```bash
# 1. Make changes to SQLModel models (backend/app/models/)

# 2. Create migration (auto-generate from model changes)
cd backend/db/migrations
alembic revision --autogenerate -m "add_user_preferences"

# 3. Review generated migration
# IMPORTANT: Always review autogenerated migrations!
# Location: backend/db/migrations/versions/YYYYMMDD_REV_add_user_preferences.py

# 4. Edit migration if needed
nano versions/YYYYMMDD_REV_add_user_preferences.py

# 5. Apply migration
alembic upgrade head

# 6. Test migration
# - Verify schema changes in database
# - Run application tests
# - Test rollback (alembic downgrade -1)

# 7. Commit migration
git add versions/YYYYMMDD_REV_add_user_preferences.py
git commit -m "feat(db): add user preferences table"
```

### Production Deployment Workflow

```bash
# 1. Pull latest code
cd ~/familyBudget && git pull

# 2. Deploy with migrations
./deploy.sh --profile full

# deploy.sh automatically:
# - Syncs code to /opt/budget
# - Restarts Docker containers
# - Runs: docker compose exec backend bash /app/backend/db/run_migrations.sh
# - Applies pending migrations via Alembic
```

## Common Operations

### Check Migration Status

```bash
# Method 1: Via run_migrations.sh
backend/db/run_migrations.sh status

# Method 2: Direct Alembic
cd backend/db/migrations
alembic current
alembic history --verbose
```

### Apply Migrations

```bash
# Apply all pending migrations
backend/db/run_migrations.sh run

# Or directly:
cd backend/db/migrations
alembic upgrade head
```

### Rollback Migration

```bash
# Rollback last migration
backend/db/run_migrations.sh downgrade

# Rollback 2 migrations
backend/db/run_migrations.sh downgrade -2

# Rollback to specific revision
cd backend/db/migrations
alembic downgrade a1b2c3d4e5f6
```

### Create New Migration

```bash
cd backend/db/migrations

# Manual migration (empty template)
alembic revision -m "add_notification_preferences"

# Auto-generate from SQLModel changes
alembic revision --autogenerate -m "sync_user_model"
```

### Database Reset (DANGER)

```bash
# WARNING: This DELETES ALL DATA!

# Method 1: Via deploy.sh
./deploy.sh --reset-db

# Method 2: Via Docker
docker compose down -v
docker compose up -d
backend/db/run_migrations.sh run
```

## Migration Best Practices

### DO ✅

1. **Always review autogenerated migrations**
   ```bash
   alembic revision --autogenerate -m "description"
   # Then: nano versions/YYYYMMDD_*.py
   ```

2. **Test migrations both ways**
   ```bash
   alembic upgrade head  # Test upgrade
   alembic downgrade -1  # Test rollback
   alembic upgrade head  # Re-apply
   ```

3. **Use descriptive messages**
   ```bash
   # Good
   alembic revision -m "add_user_email_verification"

   # Bad
   alembic revision -m "fix"
   ```

4. **Keep migrations small and focused**
   - One migration = one logical change
   - Easier to review, test, and rollback

5. **Write proper downgrade() functions**
   ```python
   def upgrade():
       op.add_column('users', sa.Column('email_verified', sa.Boolean()))

   def downgrade():
       op.drop_column('users', 'email_verified')
   ```

### DON'T ❌

1. **Don't modify applied migrations**
   - Once a migration is in production, it's immutable
   - Create a new migration to fix issues

2. **Don't skip migrations**
   ```bash
   # Bad
   alembic upgrade a1b2c3 && alembic upgrade e4f5g6

   # Good
   alembic upgrade head
   ```

3. **Don't use `pass` in downgrade()**
   ```python
   # Bad
   def downgrade():
       pass  # ← Cannot rollback!

   # Good
   def downgrade():
       op.drop_table('my_table')
   ```

4. **Don't forget to test data migrations**
   - If migration modifies data, test with realistic dataset
   - Check performance on large tables

## Troubleshooting

### Problem: "alembic command not found"

**Solution:**
```bash
# Activate virtual environment
source venv/bin/activate

# Install Alembic
pip install alembic

# Verify
alembic --version
```

### Problem: "Can't locate revision identified by 'xyz'"

**Cause:** Missing migration file or corrupted alembic_version table.

**Solution:**
```bash
# Check alembic_version table
docker compose exec postgres psql -U familybudget familybudget -c \
    "SELECT * FROM alembic_version;"

# If corrupted, reset to known good revision
cd backend/db/migrations
alembic stamp 001_baseline  # Set to baseline
alembic upgrade head        # Apply pending
```

### Problem: "Target database is not up to date"

**Cause:** Pending migrations exist.

**Solution:**
```bash
# Check pending migrations
alembic current  # Current revision
alembic heads    # Latest revision

# Apply pending migrations
alembic upgrade head
```

### Problem: Migration fails with "duplicate column" error

**Cause:** Migration already partially applied or manual schema changes.

**Solution:**
```bash
# Option 1: Skip migration (if already applied manually)
alembic stamp head

# Option 2: Fix migration to handle existing objects
# Edit migration file:
def upgrade():
    # Add IF NOT EXISTS checks
    op.execute("""
        ALTER TABLE users
        ADD COLUMN IF NOT EXISTS email VARCHAR(255)
    """)
```

### Problem: "FATAL: migration failed, cannot rollback"

**Cause:** Downgrade function is incomplete or data loss.

**Solution:**
```bash
# 1. Restore from backup
pg_restore -U familybudget -d familybudget backup.sql

# 2. Fix migration file
nano versions/YYYYMMDD_*.py
# Add proper downgrade() logic

# 3. Test migration again
alembic upgrade head
alembic downgrade -1  # Verify rollback works
```
