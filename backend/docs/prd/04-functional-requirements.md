# 04. Функциональные требования

## Обзор документа

Данный документ описывает функциональные требования к системе Family Budget, включая новую функциональность интеллектуальных рекомендаций сумм для быстрого выбора в формах транзакций и планов.

**Версия:** 1.0
**Дата:** 2025-11-04
**Статус:** Утверждено

---

## 4.1 Интеллектуальные рекомендации сумм (Smart Amount Suggestions)

### 4.1.1 Описание функциональности

Система автоматически рекомендует 4 наиболее вероятных суммы для быстрого выбора в формах ввода транзакций и планов, основываясь на исторических данных пользователя и интеллектуальных алгоритмах кластеризации.

### 4.1.2 Цель внедрения

- **Ускорить** ввод повторяющихся транзакций (продукты, транспорт, коммунальные услуги)
- **Упростить** пользовательский опыт за счет персонализации интерфейса
- **Повысить** точность планирования благодаря анализу фактических трат

### 4.1.3 Область применения

- **Telegram Web Apps:**
  - \`/webapp/add.html\` - добавление фактических транзакций
  - \`/webapp/edit.html\` - редактирование фактических транзакций
  - \`/webapp/addplan.html\` - добавление планов

### 4.1.4 Алгоритм расчета

#### Метод: K-means Clustering (Lloyd's Algorithm)

**Параметры:**
- **k = 4** - количество кластеров (соответствует 4 кнопкам быстрого выбора)
- **Период анализа:** 90 дней (квартал) - настраивается
- **Минимальный размер выборки:** 20 транзакций
- **Инициализация:** Quantile-based (10th, 35th, 65th, 90th percentiles)
- **Сходимость:** max 20 итераций, epsilon = 1.0

**Этапы алгоритма:**

1. **Сбор данных:**
   - Выбираются транзакции за последние 90 дней
   - Фильтрация по категории (опционально)
   - Фильтрация по типу (доход/расход) (опционально)
   - Фильтрация по record_type (факт/план)

2. **Проверка достаточности данных:**
   - Если транзакций < 20 → fallback к дефолтным значениям
   - Если транзакций >= 20 → выполнение K-means

3. **K-means кластеризация:**
   - Инициализация центроидов на основе квантилей
   - Итеративное присваивание точек к ближайшим центроидам
   - Пересчет центроидов как средних значений кластеров
   - Повтор до сходимости или достижения max_iterations

4. **Округление до "красивых" чисел:**
   - < 100: округление до 10 (47 → 50)
   - 100-999: округление до 50 (470 → 450)
   - 1000-9999: округление до 100 (1234 → 1200)
   - 10000-99999: округление до 500 (12345 → 12500)
   - >= 100000: округление до 10000 (123456 → 120000)

5. **Кэширование результатов:**
   - Сохранение в таблицу \`t_recommended_amounts\`
   - TTL = 24 часа
   - Ночной пересчет (scheduler, 02:00 UTC)

### 4.1.5 Дефолтные значения (fallback)

При недостатке данных (<20 транзакций) используются стандартные значения:

| Тип        | Record Type | Дефолтные суммы (₽)        |
|------------|-------------|----------------------------|
| Расход     | fact        | 100, 500, 1000, 5000       |
| Доход      | fact        | 10000, 20000, 50000, 100000|
| Расход     | plan        | 5000, 10000, 20000, 50000  |
| Доход      | plan        | 10000, 20000, 50000, 100000|

### 4.1.6 Пользовательский сценарий

**Сценарий: Быстрый ввод расхода на продукты**

1. Пользователь открывает форму добавления транзакции (\`/add\`)
2. Выбирает тип "Расход"
3. Видит 4 кнопки с рекомендуемыми суммами: \`100 ₽\`, \`500 ₽\`, \`1k ₽\`, \`5k ₽\` (дефолт)
4. Выбирает категорию "Продукты"
5. **Система автоматически обновляет кнопки** на основе истории покупок: \`300 ₽\`, \`800 ₽\`, \`1.5k ₽\`, \`3k ₽\`
6. Пользователь нажимает кнопку \`800 ₽\` (одно касание вместо ввода с клавиатуры)
7. Выбирает ЦФО, дату и сохраняет

**Экономия времени:** ~60% (1 касание вместо 3-4 для ввода суммы)

### 4.1.7 Обновление рекомендаций (UI Trigger Points)

Рекомендации обновляются в следующих случаях:

1. **Смена типа транзакции** (доход ↔ расход)
2. **Смена категории** (debounce 300ms, AbortController)
3. **Инициализация страницы**

### 4.1.8 Кэширование и производительность

**Стратегия кэширования:**
1. Проверка cache (TTL 24h)
2. On-demand расчет
3. Fallback к дефолтам

**Производительность:**
- Cache lookup: ~5ms
- On-demand K-means: ~50-200ms
- Batch recalculation: ~1-5s
