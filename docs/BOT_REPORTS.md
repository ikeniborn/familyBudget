# Отчётность Telegram-бота

Описание всех видов отчётности в Telegram-боте Family Budget: интерактивные отчёты по командам и автоматические отчёты по расписанию. С примерами вывода и описанием проблематики.

> Источники: `bot/handlers/` (today, balance, summary, list, search, export), `bot/jobs/weekly_report.py`, `bot/utils/notification_service.py`, `bot/utils/scheduler.py`.

## Общая модель данных

Все отчёты строятся из двух сущностей backend API:

| Сущность | Поля (ключевые) | Назначение |
|----------|-----------------|------------|
| **Факт** (`fact`) | `id`, `article_id`, `amount`, `fact_date`, `description`, `record_type` | Запись о деньгах |
| **Статья** (`article`) | `id`, `name`, `type` (`income`/`expense`) | Категория |

- `record_type` различает **план** (`plan`) и **факт** (`fact`) — одна сущность, два смысла.
- `article.type` (`income`/`expense`) определяет доход/расход.
- Суммы хранятся знаковыми, для отображения берётся `abs(amount)`.

Типовой пайплайн отчёта: `list_facts()` → `list_articles()` → строится `articles_map` (id → article) → группировка → форматирование Markdown.

## 1. Интерактивные отчёты (on-demand)

Запускаются командой пользователя. Все требуют авторизации (`SessionManager.is_authenticated`), JWT берётся из `context.user_data`.

| Команда | Файл | Период | API | Вывод |
|---------|------|--------|-----|-------|
| `/today` | `handlers/today.py` | Сегодня | `get_facts_summary` + `list_facts` | Текст |
| `/balance` | `handlers/balance.py` | Текущий месяц | `get_facts_summary` | Текст |
| `/summary` | `handlers/summary.py` | День/неделя/месяц/год | `list_facts` + `list_articles` | Inline-кнопки → текст |
| `/list` | `handlers/list.py` | Все | `list_facts` (limit/offset) | Пагинация |
| `/search` | `handlers/search.py` | Все | `list_facts` + фильтр | Текст |
| `/export` | `handlers/export.py` | Все | `list_facts` + `list_articles` | CSV-файл |

---

### /today — статистика за день

Итоги дня (доходы/расходы/баланс с количеством) + полный список фактов, сгруппированный по типу.

**API:** `get_facts_summary(date_from=today, date_to=today)` + `list_facts(...)`.

**Пример вывода:**

```
📊 Статистика за сегодня
📅 13.10.2025

💰 Итоги:
💵 Доходы: 5 000.00 ₽ (2 шт)
💸 Расходы: 3 500.00 ₽ (5 шт)
📈 Баланс: +1 500.00 ₽

📋 Факты:

💵 ДОХОДЫ:
• Salary: 5 000.00 ₽

💸 РАСХОДЫ:
• Groceries: 1 250.50 ₽ - Weekly shopping
• Transport: 150.00 ₽
• Utilities: 2 099.50 ₽
```

### /balance — баланс месяца

Сводный баланс текущего месяца: сумма доходов vs расходов vs итог. Самый лёгкий отчёт — только агрегат, без списка фактов.

**API:** `get_facts_summary(date_from=начало_месяца, date_to=конец_месяца)`.

**Пример вывода:**

```
💰 Баланс: Октябрь 2025
📅 01.10.2025 — 31.10.2025

💵 Доходы:  50 000.00 ₽
💸 Расходы: 38 500.00 ₽

📈 Баланс: +11 500.00 ₽
```

---

### /summary — План vs Факт

Самый богатый отчёт. Сравнивает плановые (`record_type=plan`) и фактические (`record_type=fact`) суммы по статьям. Период выбирается inline-клавиатурой.

**Поток:** `/summary` → клавиатура (Сегодня/Неделя/Месяц/Год) → `period_selected` → расчёт → текст. Реализован как `ConversationHandler` (state `SELECTING_PERIOD`).

**Логика статусов:**

| Раздел | Условие | Статус |
|--------|---------|--------|
| Доходы | факт ≥ план (≥100%) | ✅ перевыполнение |
| Доходы | факт < план (<100%) | ⚠️ недостаток |
| Расходы | факт ≤ план (≤100%) | ✅ экономия |
| Расходы | факт > план (>100%) | ⚠️ превышение |

**Пример вывода:**

```
📊 Сводка: План&Факт
📅 Месяц: 01.10.2025 - 31.10.2025

💰 ИТОГО:
План:  50 000.00 ₽
Факт:  45 500.00 ₽
Остаток: +4 500.00 ₽ (9%)

💵 ДОХОДЫ:
• Salary
  План:  50 000.00 ₽
  Факт:  50 000.00 ₽
  ✅ 100% (перевыполнение: +0.00 ₽)

💸 РАСХОДЫ:
• Food
  План:  15 000.00 ₽
  Факт:  12 500.00 ₽
  ✅ 83% (экономия: 2 500.00 ₽)

• Transport
  План:  5 000.00 ₽
  Факт:  6 000.00 ₽
  ⚠️ 120% (превышение: +1 000.00 ₽)
```

Факт без плана помечается `ℹ️ Расход без плана` / `ℹ️ Доход без плана`.

### /list — список фактов

Постраничный список всех фактов (10 на страницу) с навигацией.

**API:** `list_facts(limit=10, offset=page*10)` — единственный отчёт с серверной пагинацией.

**Пример вывода:**

```

Показано 1-10 из 47

💸 13.10.2025 | Groceries | 1 250.50 ₽
   Weekly shopping
   ID: 123

💵 13.10.2025 | Salary | 5 000.00 ₽
   ID: 124
...

[« Назад]  [2/5]  [Вперёд »]
[✅ Закрыть]
```

### /search — поиск

Поиск фактов по подстроке в описании ИЛИ названии категории (регистронезависимо).

**API:** `list_facts(limit=10000)` — тянет **все** факты, фильтрация на стороне бота. Вывод — до 20 результатов.

**Пример вывода:**

```
🔍 Результаты поиска
Запрос: "продукты"
Найдено: 3

💸 13.10.2025 | Продукты | 1 250.50 ₽
   Покупки на неделю
   ID: 123
...
```

---

### /export — выгрузка CSV

Экспорт всех транзакций в CSV-файл. UTF-8 с BOM (`utf-8-sig`) для корректного открытия в Excel.

**API:** `list_facts(limit=10000)` + `list_articles`.

**Формат CSV:**

```csv
Date,Category,Type,Amount,Description,ID
13.10.2025,Groceries,Expense,1250.50,Weekly shopping,123
13.10.2025,Salary,Income,5000.00,,124
```

Имя файла: `budget_export_2025-10-13.csv`. Отправляется как Telegram document.

## 2. Автоматические отчёты (scheduled / push)

| Тип | Файл | Триггер | Статус |
|-----|------|---------|--------|
| Еженедельный отчёт | `jobs/weekly_report.py` | APScheduler cron: вс 20:00 | ⛔ **НЕ РАБОТАЕТ** |
| Бюджетные уведомления | `utils/notification_service.py` | При достижении порога | ✅ Реализовано |

---

### Еженедельный отчёт (НЕ РАБОТАЕТ)

Должен раз в неделю (воскресенье 20:00, `scheduler.py:add_weekly_report_job`) присылать каждому пользователю сводку План&Факт за 7 дней + Топ-3 расхода.

**Текущий статус:** код форматирования (`generate_weekly_report`, `format_weekly_report`) написан полностью, но `send_weekly_reports()` отключён ранним `return`:

```python
async def send_weekly_reports(bot, user_telegram_ids=None):
    # FEATURE NOT IMPLEMENTED
    logger.debug("Weekly report job skipped - feature not implemented. "
                 "Requires persistent token storage or service account authentication.")
    return
    # ... недостижимый код ниже
```

**Причина блокировки:** scheduled job не имеет `context.user_data` → нет JWT пользователя. Нужен **persistent token storage** или **service-account аутентификация** (`API_INTERNAL_KEY`). Job регистрируется в `scheduler.py` с пустым `user_telegram_ids=[]`.

**Планируемый вид вывода:**

```
📊 Еженедельный отчет
📅 03.10.2025 - 09.10.2025

💰 Итоги недели:
План: 50 000.00 ₽
Факт: 48 500.00 ₽
✅ Экономия: +1 500.00 ₽ (3%)

📊 Топ-3 расхода:
1. Groceries: 10 000.00 ₽
2. Transport: 5 000.00 ₽
3. Utilities: 3 000.00 ₽
```

### Бюджетные уведомления

Push-алерт при приближении факта к плану по статье. Проверка за текущий месяц, порог по умолчанию **90%**.

**Логика** (`NotificationService.check_budget_threshold`):
1. Берёт план и факт по статье за месяц.
2. `percent_used = factual / plan * 100`.
3. Если ≥ порога И уведомление за период ещё не слалось (`check_duplicate_notification`) → шлёт алерт + пишет запись через `create_notification`.

**Анти-дубль:** одно уведомление на (статья + период + порог). Шлётся **только владельцу** данных (`telegram_id`), не broadcast — отмечено как SECURITY FIX в коде.

**Пример вывода (≥100%):**

```
🚨 Бюджетное предупреждение
---
ЦФО: Семья
Категория: Food
Статус: ПРЕВЫШЕН
---
Статистика:
План: 15 000.00 ₽
Факт: 16 500.00 ₽
Использовано: 110%
Превышение: +1 500.00 ₽
```

Статусы: `⚠️ ДОСТИГНУТ ПОРОГ` (≥90%), `🚨 ПРЕВЫШЕН` (≥100%).

## Проблематика

### Критичное

1. **Еженедельный отчёт не работает.** Главный proactive-отчёт отключён. Корень — отсутствие persistent token storage / service-account для scheduled jobs. Без него бот не может проактивно тянуть данные пользователей. Решение: реализовать `API_INTERNAL_KEY`-аутентификацию для job'ов (см. правило 10 в `fb-bot` skill).

2. **Битая ссылка `/stats`.** `today.py` и footer'ы ссылаются на команду `/stats` («или /stats для общей статистики»), но handler **не зарегистрирован** в `bot.py`. Пользователь получает «команда не найдена». Решение: либо реализовать `/stats`, либо убрать ссылки.

### Производительность

3. **Перетягивание всех фактов.** `/search`, `/export`, `/summary`, бюджетные уведомления вызывают `list_facts(limit=10000)` и обрабатывают данные на стороне бота. Backend не имеет:
   - серверного поиска (фильтрация в `/search` — client-side);
   - серверной агрегации по статьям (группировка для `/summary` — в боте).

   На больших объёмах → рост latency и нагрузки. Решение: добавить backend-эндпоинты поиска и агрегации (`GET /facts/search`, расширить `/facts/summary` группировкой по статьям).

4. **N запросов статей в каждом отчёте.** Почти каждый отчёт повторно тянет `list_articles(limit=1000)`. Кандидат на кэш в `api_client` (статьи меняются редко).

### UX / консистентность

5. **`/help` неполон.** Не упоминает `/balance` и `/summary` — пользователь не узнаёт про главный отчёт План&Факт. Решение: дополнить `format_authenticated_help`.

6. **Нет фильтра по категории/типу в отчётах.** `/list` показывает всё подряд; нельзя отфильтровать только расходы или конкретную статью. `/summary` — только по периоду.

7. **Лимит вывода поиска 20 без указания усечения по сумме.** `/search` показывает «...и ещё N результатов», но без агрегата (сколько всего потрачено по найденным) — теряется аналитическая ценность.

### Безопасность / надёжность

8. **Fail-open в анти-дубле уведомлений.** При ошибке `check_duplicate_notification` сервис считает «не слалось» и шлёт повторно (`notification_service.py:_notification_already_sent`). Возможен спам уведомлениями при сбоях backend. Компромисс осознанный (fail-safe = доставить), но стоит ограничить rate.
