Authentication Architecture¶

Overview¶

Family Budget supports multiple authentication methods with mandatory 2FA for regular users and optional bypass for administrators.

Supported Authentication Methods¶

Method

2FA Required

Use Case

Telegram OAuth

No (built-in Telegram security)

Primary method (recommended)

Email + Password + 2FA

Yes (mandatory for regular users)

Alternative for non-Telegram users

Email + Password (Admin Only)

No (security exception)

Emergency admin access

Key Security Features¶

  • HMAC-SHA256 Telegram OAuth validation

  • Argon2id password hashing (memory-hard, GPU-resistant)

  • TOTP-based 2FA (Time-based One-Time Password)

  • JWT tokens with httpOnly cookies (access: 7 days, refresh: 30 days)

  • Token rotation (old refresh tokens revoked)

  • Rate limiting (5 login attempts per minute per IP)

  • Comprehensive logging (all authentication events tracked)

Authentication Methods¶

1. Telegram OAuth (Recommended)¶

Flow:

  1. User clicks “Login with Telegram” button

  2. Telegram Widget validates user via HMAC-SHA256

  3. Backend receives validated Telegram data

  4. Backend creates/updates user in database

  5. Backend generates JWT tokens and sets httpOnly cookies

  6. User redirected to dashboard

Security:

  • No password storage required

  • Telegram handles 2FA (if enabled in Telegram)

  • HMAC validation prevents data tampering

  • User data auto-synced from Telegram profile

Code:

# backend/app/api/v1/endpoints/auth.py
@router.post("/telegram")
async def telegram_login(data: TelegramAuthData, ...):
    # Validate HMAC-SHA256 signature
    if not validate_telegram_auth(data, settings.TELEGRAM_BOT_TOKEN):
        raise HTTPException(401, "Invalid Telegram data")

    # Create or update user
    user = await get_user_by_telegram_id(session, data.id)
    if not user:
        user = User(telegram_id=data.id, ...)

    # Generate tokens
    access_token = create_access_token(user_id=user.id)
    refresh_token, expires = create_refresh_token(user_id=user.id)

    return AuthResponse(user=..., access_token=..., refresh_token=...)

2. Email + Password + 2FA (Regular Users)¶

Flow:

  1. User enters email + password

  2. Backend validates credentials (timing-safe)

  3. Backend creates 2FA session (5-minute TTL)

  4. User redirected to:

    • /2fa-setup-login if first-time (QR code setup)

    • /2fa-verify if 2FA already configured

  5. User enters TOTP code from authenticator app

  6. Backend validates code and generates JWT tokens

  7. User redirected to dashboard

Security:

  • Mandatory 2FA for all regular users

  • Argon2id password hashing (OWASP 2023)

  • TOTP codes expire after 30 seconds

  • Backup codes for 2FA recovery (10 codes, single-use)

  • Session tokens expire after 5 minutes

Code:

# backend/app/api/v1/endpoints/auth.py
@router.post("/login")
async def login_email(data: EmailLoginRequest, ...):
    # Authenticate with email/password
    user = await authenticate_with_password(session, data.email, data.password)

    # Regular users ALWAYS require 2FA
    if not user.is_admin:
        session_token = await create_2fa_session(session, user.id)

        if not user.two_factor_enabled:
            # Setup 2FA first time
            return EmailLoginResponse(
                requires_2fa_setup=True,
                session_token=session_token,
                totp_secret=generate_secret(),
                ...
            )
        else:
            # Verify existing 2FA
            return EmailLoginResponse(
                requires_2fa=True,
                session_token=session_token
            )

3. Email + Password (Admin Bypass)¶

⚠️ SECURITY EXCEPTION: Admins can login WITHOUT 2FA for emergency access.

Flow:

  1. User enters email + password

  2. Backend validates credentials (timing-safe)

  3. Admin bypass check: if user.is_admin:

  4. Backend generates JWT tokens directly (skip 2FA)

  5. Backend sets httpOnly cookies

  6. User redirected to dashboard immediately

Security Measures:

  • Strong password requirements (OWASP 2023):

    • Minimum 24 characters (auto-generated by setup.sh)

    • Uppercase + lowercase + digit + special character

    • Not in top 100 common passwords

  • Rate limiting: 5 attempts per minute per IP

  • Comprehensive logging:

    • All login attempts logged with IP address

    • Failed attempts flagged with [AUTH_EMAIL] prefix

    • Admin bypass events clearly marked

Code:

# backend/app/api/v1/endpoints/auth.py
@router.post("/login")
async def login_email(
    request: Request,
    response: Response,  # For setting cookies
    data: EmailLoginRequest,
    ...
) -> EmailLoginResponse | AuthResponse:  # Union return type

    user = await authenticate_with_password(session, data.email, data.password)

    # ========================================================================
    # ADMIN BYPASS: Skip 2FA for admin users (SECURITY EXCEPTION)
    # ========================================================================
    if user.is_admin:
        logger.info(
            f"[AUTH_EMAIL] Admin login bypass: user_id={user.id}, "
            f"bypassing 2FA requirement, ip={request.client.host}"
        )

        # Generate JWT tokens directly
        access_token = create_access_token(user_id=user.id, ...)
        refresh_token, refresh_expires = create_refresh_token(user_id=user.id)

        # Store refresh token in DB
        db_refresh_token = RefreshToken(...)
        session.add(db_refresh_token)

        # Update last login
        user.last_login_at = datetime.utcnow()
        await session.commit()

        # Set httpOnly cookies
        response.set_cookie(
            key="access_token",
            value=access_token,
            httponly=True,
            secure=True,  # production only
            samesite="lax",
            max_age=60 * 60 * 24 * 7,  # 7 days
        )
        response.set_cookie(key="refresh_token", ...)

        # Return AuthResponse (includes tokens)
        return AuthResponse(
            user=...,
            message="Admin authentication successful (2FA bypassed)",
            access_token=access_token,
            refresh_token=refresh_token,
        )

    # Regular user flow: require 2FA (existing logic)
    session_token = await create_2fa_session(session, user.id)
    ...

Why Admin Bypass Exists:

  • Emergency access if 2FA device lost

  • System recovery scenarios

  • Administrator discretion on security vs convenience

Risks and Mitigations:

Risk

Mitigation

Password compromise

24-char auto-generated password, Argon2id hashing

Brute force attacks

Rate limiting (5/min), account lockout (future)

Credential stuffing

Password strength validation, monitoring

Unauthorized access

Comprehensive logging, regular audit

Frontend Detection¶

Admin Bypass Detection (JavaScript)¶

Frontend detects admin bypass by checking response schema:

EmailLoginResponse (regular users):

{
  "requires_2fa": true,
  "requires_2fa_setup": false,
  "session_token": "abc123...",
  "expires_in": 300
}

AuthResponse (admin bypass):

{
  "user": {...},
  "message": "Admin authentication successful (2FA bypassed)",
  "access_token": "eyJ...",
  "refresh_token": "eyJ...",
  "token_type": "bearer"
}

Frontend code:

// frontend/web/templates/login_email.html
const response = await fetch('/api/v1/auth/login', {...});
const data = await response.json();

// Admin bypass detection
if (data.access_token && data.refresh_token) {
    console.log('[AUTH_EMAIL] Admin bypass detected - JWT tokens received');
    console.log('[AUTH_EMAIL] Redirecting to dashboard (2FA skipped)');
    window.location.href = '/';
    return;
}

// Regular user: 2FA flow
if (data.requires_2fa_setup && data.session_token) {
    console.log('[AUTH_EMAIL] Regular user: 2FA setup required');
    window.location.href = '/2fa-setup-login';
} else if (data.requires_2fa && data.session_token) {
    console.log('[AUTH_EMAIL] Regular user: 2FA verification required');
    window.location.href = '/2fa-verify';
}

Database Models¶

User Model (SCD Type 1 + History)¶

# backend/app/models/user.py
class User(SQLModel, table=True):
    __tablename__ = "t_d_user"

    id: int | None = Field(default=None, primary_key=True)
    telegram_id: int | None = Field(default=None, unique=True, index=True)
    email: str | None = Field(default=None, unique=True, index=True)
    password_hash: str | None = None  # Argon2id hashed

    is_admin: bool = Field(default=False)
    is_active: bool = Field(default=True)

    two_factor_enabled: bool = Field(default=False)
    two_factor_secret: str | None = None  # TOTP secret
    backup_codes: str | None = None  # Encrypted backup codes

    last_login_at: datetime | None = None
    created_at: datetime = Field(default_factory=datetime.utcnow)
    updated_at: datetime = Field(default_factory=datetime.utcnow)

RefreshToken Model¶

# backend/app/models/refresh_token.py
class RefreshToken(SQLModel, table=True):
    __tablename__ = "t_d_refresh_token"

    id: int | None = Field(default=None, primary_key=True)
    user_id: int = Field(foreign_key="t_d_user.id", index=True)
    token_hash: str  # SHA-256 hashed
    expires_at: datetime
    created_at: datetime = Field(default_factory=datetime.utcnow)

Security Best Practices¶

For Administrators¶

  1. Use Telegram OAuth when possible (more secure than email/password)

  2. Change auto-generated password after first login (optional but recommended)

  3. Enable voluntary 2FA via web UI (admin bypass remains as fallback)

  4. Monitor authentication logs regularly:

    docker compose logs backend | grep "\[AUTH_EMAIL\]"

  5. Restrict admin email/password to trusted networks (future: IP allowlist)

For Regular Users¶

  1. Always enable 2FA for email/password login (mandatory)

  2. Save backup codes securely (10 single-use codes for 2FA recovery)

  3. Use strong unique password (minimum 12 characters)

  4. Prefer Telegram OAuth over email/password (simpler, more secure)

For Developers¶

  1. Never log passwords (plain text or hashed)

  2. Always verify timing-safety of authentication functions

  3. Test admin bypass thoroughly (unit tests + manual testing)

  4. Monitor failed login attempts (potential brute force attacks)

  5. Use rate limiting aggressively (prevent credential stuffing)

WebAuthn Endpoint Authentication Pattern¶

All WebAuthn endpoints use FastAPI dependency injection for authentication (consistent with rest of codebase).

Correct Pattern¶

from backend.app.core.dependencies import CurrentUser

@router.post("/webauthn/register/options")
async def register_options(
    request: Request,  # Optional: for IP/user-agent extraction
    current_user: CurrentUser,  # ✅ Dependency injection
    session: AsyncSession = Depends(get_session),
) -> dict:
    # current_user is automatically loaded from database
    # Includes validation: user exists, is active

    logger.info(f"[WEBAUTHN] User {current_user.id} requested registration")

    # Use current_user directly - no manual checks needed
    return await create_registration_challenge(session, current_user)

Incorrect Pattern (Historical Reference)¶

# ❌ WRONG - DO NOT USE
@router.post("/webauthn/register/options")
async def register_options(
    request: Request,
    session: AsyncSession = Depends(get_session),
) -> dict:
    # ❌ Manual check - inconsistent with codebase
    if not hasattr(request.state, "user"):
        raise HTTPException(401, "Authentication required")

    # ❌ request.state.user is NEVER set by JWT middleware
    user: User = request.state.user

Why Manual Checks Fail:

  • JWT middleware sets request.state.user_id (NOT request.state.user)

  • Middleware doesn’t load User object from database

  • Manual pattern duplicates get_current_user logic

  • Inconsistent with rest of codebase

WebAuthn Onboarding During First Login (v6.5.1+)¶

Since version 6.5.1: Users are prompted to enable biometric authentication immediately after 2FA setup during first login.

Flow¶

First-Time Login:
1. User enters email + password
2. POST /api/v1/auth/login → requires_2fa_setup=true
3. User redirected to /2fa-setup-login
4. User scans QR code → enters TOTP code
5. POST /api/v1/auth/setup-and-verify-2fa → JWT tokens set in cookies
6. Step 2: Backup codes displayed
7. User confirms saving backup codes
8. **Step 3 (NEW):** WebAuthn onboarding prompt shown
   - Check browser support
   - Check platform authenticator availability
   - Check localStorage flag (not dismissed before)
9. User choices:
   a) "Включить биометрию" → WebAuthn registration flow
   b) "Пропустить" → Set dismissal flag, redirect to dashboard

WebAuthn Registration (Step 3):
1. POST /api/v1/webauthn/register/options (JWT auth)
2. navigator.credentials.create() → TouchID/FaceID prompt
3. POST /api/v1/webauthn/register/verify with credential
4. Success → Redirect to dashboard with toast
5. sessionStorage flag 'from_2fa_setup_login' prevents duplicate modal

Implementation Details¶

Frontend: frontend/web/templates/2fa_setup_login.html

  • Step 3 div: #step-webauthn-onboarding (hidden by default)

  • Trigger: finishSetup() checks checkWebAuthnAvailability()

  • Registration: handleEnableWebAuthnOnboarding() function

  • Skip: skipWebAuthnOnboarding() sets localStorage flag

Backend: backend/app/api/v1/endpoints/auth.py

  • Endpoint: GET /api/v1/auth/webauthn-status (authenticated)

  • Returns: {has_credentials: bool, user_id: int}

  • Used by: webauthn-onboarding.js on dashboard

Logging Prefixes:

  • Frontend: [2FA_SETUP_LOGIN][WEBAUTHN_CHECK], [2FA_SETUP_LOGIN][WEBAUTHN_REG]

  • Backend: [WEBAUTHN_STATUS]

Security Considerations¶

  • JWT tokens are already set when Step 3 appears (after /setup-and-verify-2fa)

  • WebAuthn registration requires valid JWT cookie (same as /security page)

  • Dismissal flag stored in localStorage (per-device, not per-account)

  • No security downgrade - 2FA remains mandatory for email login

User Experience¶

Benefits:

  • Immediate biometric setup (while user is engaged)

  • Reduces friction for future logins

  • Optional (can skip and enable later)

Fallbacks:

  • Browser doesn’t support WebAuthn → Skip step 3 automatically

  • No biometric device → Skip step 3 automatically

  • User dismissed before → Skip step 3 automatically

  • User skips → Can enable later via /security page
