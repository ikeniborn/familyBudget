# Realtime

Family Budget pushes live updates over a WebSocket so every member of the shared family budget sees facts, plans, transfers, and shopping-list changes the instant they happen. Redis underpins the whole system: it fans WebSocket events out across uvicorn workers, backs a read-through cache, queues write-behind persistence, and stores the long-polling event buffer. Layered on top are Web Push (for offline users), Telegram and in-app notifications, and scheduled reminders. The endpoints described here are served under `/api/v1` — see [[api]] for routing — and the browser-side WebSocket client lives in [[frontend]].

## Redis Service

The shared Redis connection pool and the foundation every feature on this page builds on. Redis is optional: `is_redis_available()` gates all callers so the app degrades gracefully when it is down.

`init_redis_pool()` (called on app startup) builds a `ConnectionPool.from_url(REDIS_URL, max_connections=20, decode_responses=True)`; every consumer acquires a client through the `get_redis()` async context manager. `backend/app/services/redis_service.py` also exposes health and monitoring helpers used by the admin dashboard: `check_redis_health()` (PING latency plus `INFO memory/stats/keyspace`), `get_redis_stats()`, and `get_cache_breakdown()` (counts `cache:*` keys grouped by the `cache:{category}:...` prefix). The Redis container is defined in `docker-compose.yml` as `familybudget-redis` with `--maxmemory 256mb --maxmemory-policy allkeys-lru --appendonly yes --requirepass`, so cache keys are evicted LRU under memory pressure while AOF persists the write-behind queue and event buffer.

## WebSocket Endpoint

`GET /api/v1/budget/ws?token=...` (`backend/app/api/v1/endpoints/budget_ws.py`) is the real-time channel. Because WebSockets cannot send cookies, the client first mints a short-lived token, then connects with it as a query parameter.

The token comes from `POST /budget/ws/token`: a 5-minute JWT carrying a `type: ws` claim. `verify_ws_token()` decodes it via `decode_ws_token` and rejects ordinary API tokens. This is a **shared-budget broadcast model**: every authenticated user receives every event. Server→client message types include `connected`, `ping`/`pong`, `online_status`, and the data events `fact_created/updated/deleted`, `plan_created/updated/deleted`, `transfer_created/deleted`, and `item_created/updated/deleted/completed`. Client→server it accepts `{"type":"ping"}` and `{"type":"check_online"}`. A background `send_pings()` task emits a keepalive every `WS_KEEPALIVE_INTERVAL` (10 s); every `USER_STATUS_CHECK_INTERVAL` (5 min) the loop re-checks `User.is_active` and disconnects deactivated users. Companion HTTP routes: `GET /budget/ws/status`, `POST /budget/ws/disconnect` (called via `sendBeacon` on tab close), and the `GET /budget/poll` long-polling fallback. JWT minting is covered in [[auth]]; the JS client in [[frontend]].

## Redis Pub/Sub Fan-out

`backend/app/services/redis_pubsub_service.py` synchronizes WebSocket events across uvicorn workers, since a `WebSocket` object only lives on the worker that holds it. Events flow through the `budget:events` channel.

`publish_event(event_type, data, source_worker_id)` writes to the channel; each worker runs a `_subscriber_loop()` background task (started by `start_pubsub_listener`) that consumes it with `pubsub.get_message(timeout=1.0)` and forwards each event to its local connections through a registered callback. To avoid double-delivery, the publishing worker stamps `source_worker_id` and subscribers skip events that match their own worker id. The same module maintains a **Redis event buffer** — a ZSET (`budget:event_buffer`) scored by Unix timestamp, trimmed to `EVENT_BUFFER_MAX_AGE` (60 s) and `EVENT_BUFFER_MAX_SIZE` (1000). `get_events_since(timestamp)` reads it; this is what the long-polling fallback in [[realtime#WebSocket Endpoint]] replays so HTTP-only clients still catch missed events. The loop reconnects with a 5 s backoff on `RedisConnectionError`.

## Multi-Worker WS Manager

`RedisBudgetWebSocketManager` (`backend/app/services/redis_ws_manager.py`, singleton via `get_ws_manager()`) is the connection registry the endpoint uses. Each worker holds its own connections and is identified by a per-instance `_worker_id` (UUID).

Connections are stored as `(user_id, websocket, connection_id, last_activity)` tuples guarded by an `asyncio.Lock`. Per-worker security limits apply: `MAX_CONNECTIONS_PER_USER` (10) and `MAX_TOTAL_CONNECTIONS` (500) raise HTTP 429; `cleanup_stale_connections()` drops connections idle past `STALE_CONNECTION_TIMEOUT` (60 s), driven by a periodic 30 s cleanup task. `broadcast(event_type, data)` is the key path: it **always** delivers to local connections first (so events are never silently dropped), then — if Redis is available — calls `publish_event(..., source_worker_id=self._worker_id)` so other workers receive it through [[realtime#Redis Pub/Sub Fan-out]] and forward to their own clients via the registered `_local_broadcast` callback. A `RedisEventBuffer` wrapper backs long polling, falling back to an in-memory `deque` when Redis is absent. When Redis is unavailable the manager works in single-worker, in-memory mode.

## Write-Behind Cache

`backend/app/services/write_behind_service.py` decouples PostgreSQL writes from the API response for budget facts, lowering write latency. It is active only when `WRITE_BEHIND_ENABLED` and Redis is available.

A fact create/update/delete is serialized to the Redis list `write_queue:facts` (RPUSH) and the endpoint returns immediately using a pre-generated sequence id — faster than a synchronous commit. A single background worker (`_worker_loop`) holds a Redis lock (`write_queue:facts:lock`, `SET NX EX 30`, periodically refreshed), `BLPOP`s items, and applies them. Processing each item (`_process_fact`) writes the `BudgetFact` row **and** a full `BudgetFactHistory` SCD record (CREATE/UPDATE/DELETE change types, closing the prior current row), then invalidates the dashboard cache, commits, and broadcasts the WebSocket event via the manager in [[realtime#Multi-Worker WS Manager]]. Failures retry with exponential backoff (100 ms → 5 s) up to `WRITE_BEHIND_MAX_RETRIES`, after which the item moves to a Dead Letter Queue (`write_queue:facts:failed`) that is size-capped and TTL-pruned. `get_queue_stats()` exposes queue/DLQ depth. The history schema is described in [[database]]; the fact domain in [[domain]].

## Cache Service & Metrics

`backend/app/services/cache_service.py` is a read-through cache (singleton `cache_service`) for reference and dashboard data. Every method no-ops gracefully when Redis is down, falling back to the database.

`get_or_set(key, fetch_fn, ttl)` returns the cached value or fetches, caches, and returns it; all keys are namespaced `cache:{prefix}:{parts}` via the `CacheKey` builder (articles, financial_centers, cost_centers, recurring_plans, dashboard, recent). TTLs come from settings through `CacheTTL`: REFERENCE (300 s), DASHBOARD (30 s), DYNAMIC (60 s), SHORT (10 s). Mutations invalidate by glob pattern — `invalidate_pattern()` uses `SCAN` with a 1000-key safety cap, wrapped by helpers like `invalidate_dashboard()` and `invalidate_recurring_plans(user_id)`. A separate, server-side **client cache metrics** service (`cache_metrics_service.py`, in-memory with a 5 min TTL) aggregates browser-reported stats (Service Worker cache, IndexedDB, Storage Quota, local/session storage). Browsers POST snapshots to `POST /api/v1/admin/cache-metrics` (public, returns 202) and admins read the aggregate at `GET /api/v1/admin/cache-metrics` (`backend/app/api/v1/endpoints/cache_metrics.py`). This client-metrics feature is admin monitoring only and is unrelated to the Redis server cache.

## Push Notifications

Web Push reaches users whose tabs are closed. `backend/app/services/push_service.py` (`PushService`) sends VAPID-signed notifications with `pywebpush`.

`is_configured()` validates that `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` are real (not placeholders, ≥65 chars). On a `410 Gone` response the expired subscription is deleted. Key methods: `send_to_user`, `broadcast_all`, and `broadcast_except_connected(connected_user_ids, ...)` — the latter is the integration point with the live channel: users with an open connection get the in-app event, everyone else gets a push (one per user). The budget WebSocket layer calls this via `_send_push_for_offline_users`, debounced to one push per 30 s. Subscriptions are managed at `POST /api/v1/push/subscribe` and `/push/unsubscribe`, with the public `GET /push/vapid-key` returning the server's public key; `POST /push/notify` is an admin-only test sender (`backend/app/api/v1/endpoints/push.py`). Each subscription is a `PushSubscription` row (`t_push_subscription`: `endpoint`, `p256dh_key`, `auth_key`, `user_agent`, `last_used_at`) cascade-deleted with the user — see [[database]]. PWA browser support and the service worker are covered in [[frontend]].

## In-App Notifications

The `Notification` model (`t_notification`, `backend/app/models/notification.py`) is a transactional history table (no SCD) of budget alerts. A NULL `user_id` marks a **broadcast** notification sent to all family members.

A unique constraint prevents duplicate broadcasts for the same article and period. Stored fields include `notification_type` (`budget_threshold`, `budget_exceeded`, `weekly_report`), `threshold_percent`, `plan_amount`, `actual_amount`, and the `period_start`/`period_end` window. `backend/app/services/notification_service.py` produces these in scheduler jobs: `send_weekly_reports()` (weekly Telegram summary of plan vs. fact) and `check_all_budget_thresholds()` (per-article current-month check that messages users and records a broadcast `Notification` when usage ≥ 90%). Both honor each `User.enable_telegram_notifications` flag and send through the Telegram Bot API (see [[bot]]). The REST surface in `backend/app/api/v1/endpoints/notifications.py` lets the bot create records (`POST /notifications`, internal API key), check duplicates (`GET /notifications/check-duplicate`), and list history (`GET /notifications`) — listing is intentionally un-scoped so all members see the same shared-budget history.

## Scheduled Reminders

`ScheduledReminder` (`t_scheduled_reminder`, `backend/app/models/scheduled_reminder.py`) attaches a one-off reminder to a budget plan (a `BudgetFact` with `record_type='plan'`), unique per `fact_id`.

It tracks a `status` lifecycle (`pending` → `sent`/`failed`/`cancelled`) and per-channel send flags. The model stores `reminder_datetime` (naive, in `SYSTEM_TIMEZONE`), `telegram_sent`/`web_push_sent` flags, and a `retry_count` (max 3). CRUD is exposed at `POST|GET|PUT|DELETE /api/v1/reminders/{fact_id}` plus `GET /reminders/` (`backend/app/api/v1/endpoints/reminders.py`); each mutation invalidates the `recent:html:*` cache keys so the reminder icon updates immediately. `ReminderService.send_reminder()` (`backend/app/services/reminder_service.py`) dispatches due reminders through two channels — Telegram (when `enable_telegram_notifications`) and Web Push via `_send_web_push_to_user` (when `enable_push_notifications`) — marking the reminder `sent` if either succeeds and retrying otherwise. The parallel `MedicineReminderService` drives per-intake medicine alerts over the same Telegram + Web Push channels (gated by the course's `notification_channels`) and adds snooze handling; the medicine domain, intake logging, and dispatch scheduler are documented in [[medicine]].
